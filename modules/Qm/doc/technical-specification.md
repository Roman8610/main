# Техническое задание
## Модуль постановочных вопросов к совещаниям Qm

**Версия документа:** 1.0  
**Основание:** анализ текущей реализации модуля `modules/Qm`  
**Статус:** описание фактически реализованного поведения и перечень ограничений

## 1. Назначение

Модуль предназначен для постановки вопросов в рамках совещания, их адресации дочерним обществам, подготовки и прохождения модерации, публикации для участников совещания, а также обсуждения опубликованных вопросов в виде дерева комментариев.

Модуль использует существующие сущности совещаний, дочерних обществ, подразделений и пользователей приложения. Собственной интеграции с модулем совещаний и собственной RBAC-модели не содержит.

## 2. Основные сущности

### 2.1. Постановочный вопрос

Таблица `meeting_questions`.

| Поле | Назначение | Обязательность |
|---|---|---|
| `id` | Идентификатор вопроса | Да |
| `meeting_id` | Совещание | Да |
| `name` | Название вопроса | Да |
| `question_text` | Текст вопроса | Да |
| `decision` | Предполагаемое решение | Нет |
| `comment` | Комментарий автора | Нет |
| `deadline` | Предлагаемый срок выполнения | Нет |
| `created_at` | Дата создания | Да |
| `updated_at` | Дата последнего изменения | Нет |
| `created_by` | Автор вопроса | Да |
| `updated_by` | Пользователь, изменивший вопрос | Нет |
| `comment_moderator` | Причина отклонения | Нет |
| `directions` | Направление, указанное при публикации | Нет |
| `status` | Текущий статус | Да |

### 2.2. Адресат вопроса

Таблица `recipients_questions` связывает вопрос с таблицей `subsidiary`. Один вопрос может иметь несколько адресатов. При редактировании полный список адресатов заменяется заново.

### 2.3. Отдел вопроса

Таблица `departments_questions` связывает опубликованный вопрос с таблицей `departments`. Отделы выбираются модератором при публикации; при повторной публикации текущий список заменяется.

### 2.4. Комментарий

Таблица `comment_questions` содержит комментарий к вопросу или ответ на другой комментарий:

- `question_id` — вопрос;
- `parent_id` — родительский комментарий, допускает вложенность;
- `text` — текст;
- `created_at`, `updated_at` — даты.

Удаление родительского комментария каскадно удаляет дочерние комментарии. Автор комментария в текущей схеме не хранится.

## 3. Статусы и переходы

Используются статусы:

- `draft` — черновик;
- `pending` — на модерации;
- `published` — опубликован;
- `rejected` — отклонён модератором;
- `removed` — снят с публикации.

Фактически доступные переходы:

```text
draft -> pending
pending -> published
pending -> rejected
published -> removed
removed -> published
removed -> rejected
```

При создании вопроса пользователь выбирает одно из действий:

- сохранить черновик (`save_draft`);
- сразу отправить на модерацию (`submit_pending`).

Отдельный пользовательский action для повторной отправки `rejected` или `removed` на модерацию отсутствует, хотя внутренний сервис отправки на модерацию существует.

## 4. Роли

В контексте совещания предусмотрены роли:

- `admin` — администратор портала;
- `moderator` — руководитель совещания/модератор;
- `user_do` — сотрудник дочернего общества;
- `attendee` — участник совещания;
- `responsible` — ответственный в филиале.

Текущая реализация временно определяет роли по фиксированным идентификаторам пользователей:

- администратор — `666`;
- модератор — `200`;
- сотрудник дочернего общества — `300`;
- ответственный — `400`;
- участник — `500`.

Идентификатор совещания при этих проверках фактически не учитывается.

## 5. Матрица доступа

| Операция | Текущее правило |
|---|---|
| Просмотр совещаний | Авторизованный пользователь |
| Создание вопроса | Администратор, модератор, сотрудник ДО, ответственный или участник |
| Просмотр своего вопроса | Автор, независимо от статуса |
| Просмотр чужого `pending`, `rejected`, `removed` | Модератор |
| Просмотр чужого `published` | Пользователь с любой определённой ролью |
| Просмотр вопросов в списке совещания | Администратор — все; модератор — всё, кроме чужих черновиков; остальные роли — свои и опубликованные |
| Редактирование вопроса | Только автор, если статус не `pending` и не `published` |
| Удаление вопроса | Только автор, если статус не `pending`; при наличии комментариев удаление запрещено |
| Модерация | Текущий модератор (`200`) для `pending` и `removed` |
| Публикация | Текущий модератор для `pending` и `removed` |
| Снятие с публикации | Текущий модератор для `published` |
| Добавление комментария | Для опубликованного вопроса |
| Редактирование/удаление комментария | В текущей реализации фактически разрешено без проверки автора |

Вызовы, изменяющие состояние, защищены POST-методом для удаления, публикации, отклонения и снятия с публикации.

## 6. Пользовательские сценарии

### 6.1. Просмотр совещаний

1. Авторизованный пользователь открывает список совещаний.
2. Система отображает записи из `meetings`.
3. Пользователь открывает совещание.
4. Система показывает доступные ему постановочные вопросы с названием, автором, адресатами, статусом и действиями.
5. Пользователь может открыть форму добавления вопроса.

### 6.2. Создание вопроса

Пользователь заполняет:

- название;
- текст вопроса;
- одного или нескольких адресатов из справочника дочерних обществ;
- предлагаемый срок выполнения;
- предполагаемое решение;
- комментарий автора.

Обязательны название, текст и адресаты. При сохранении создаётся запись со статусом `draft`. При отправке на модерацию после сохранения статус меняется на `pending`. Запись вопроса и адресатов выполняется в одной транзакции.

### 6.3. Редактирование вопроса

Автор может изменить свой черновик, отклонённый или снятый с публикации вопрос. При сохранении обновляются содержательные поля, даты изменения, пользователь-редактор и полный список адресатов. Вопрос можно сохранить либо отправить на модерацию.

### 6.4. Модерация и публикация

Модератор открывает вопрос в статусе `pending` или `removed` и выбирает:

- отделы из справочника;
- направление.

При публикации статус устанавливается в `published`, направление сохраняется, выбранные отделы перезаписываются. Все изменения выполняются транзакционно.

### 6.5. Отклонение

Модератор указывает обязательную причину отклонения. Причина сохраняется в `comment_moderator`, статус устанавливается в `rejected`.

### 6.6. Снятие с публикации

Модератор снимает опубликованный вопрос. Статус меняется на `removed`; содержимое, адресаты и отделы сохраняются.

### 6.7. Комментирование

Для опубликованного вопроса пользователь может добавить ответ. В комментарии допускается `parent_id`, поэтому ответы отображаются вложенным деревом. Доступны операции создания, редактирования и удаления комментария.

Перед удалением вопроса контроллер проверяет наличие комментариев и требует удалить их заранее.

## 7. Валидация данных

- `name`, `question_text`, `recipients` — обязательны;
- `deadline` — дата в формате `yyyy-MM-dd`;
- `recipients`, `departments` — массив целых чисел;
- `comment`, `decision`, `question_text`, `directions` — строки;
- для публикации обязательны `departments`, `directions`, `question_id`;
- для отклонения обязательны `comment_moderator`, `question_id`;
- для комментария обязательны `question_id`, `text`;
- для удаления обязателен целочисленный идентификатор объекта.

## 8. Интерфейс и маршруты

### Совещания

- `Qm/meetings` — список совещаний;
- `Qm/meetings/view?id={id}` — совещание и доступные вопросы.

### Вопросы

- `Qm/meeting-question/create?id={meetingId}` — создание;
- `Qm/meeting-question/update?id={id}` — редактирование;
- `Qm/meeting-question/view?id={id}` — просмотр;
- `Qm/meeting-question/moderation?id={id}` — модерация;
- `Qm/meeting-question/publish` — публикация, POST;
- `Qm/meeting-question/reject` — отклонение, POST;
- `Qm/meeting-question/off` — снятие с публикации, POST;
- `Qm/meeting-question/delete` — удаление, POST.

### Комментарии

- `Qm/question-comments/create?id={questionId}` — создание ответа;
- `Qm/question-comments/update?id={commentId}` — редактирование;
- `Qm/question-comments/delete` — удаление, POST.

## 9. Нефункциональные требования текущей реализации

- Приложение работает в Yii 2.
- Сервисы модуля регистрируются компонентами в `config/web.php`.
- Операции массовой замены адресатов и отделов выполняются в транзакциях.
- Просмотр списка вопросов использует фильтрацию по роли и `ActiveDataProvider`.
- Дерево комментариев строится серверным виджетом `CommentsWidget`.
- Ошибки доступа возвращаются как HTTP 403, отсутствующие сущности — как HTTP 404.

## 10. Ограничения и обязательные вопросы к доработке

Следующие пункты являются особенностями или незавершёнными местами текущей реализации и должны быть согласованы перед переводом модуля в промышленную эксплуатацию:

1. Заменить фиксированные ID пользователей на реальную систему ролей, состав участников совещания и привязку модератора к конкретному совещанию.
2. Уточнить права администратора: сейчас он видит вопросы в списке, но не получает права модерации и прямого просмотра всех статусов через `canView()`.
3. Добавить автора комментария и проверять, что редактировать/удалять комментарий может только его автор либо уполномоченный модератор.
4. Исправить сценарий `actionUpdate()` комментария: сервис вызывается даже при невалидной форме.
5. Добавить отдельную отправку отклонённого или снятого вопроса на повторную модерацию либо формально исключить такой сценарий.
6. Проверять существование совещания, дочерних обществ, отделов и родительского комментария.
7. Добавить внешние ключи и уникальные ограничения для таблиц связей, если это допускает схема проекта.
8. Уточнить требование к удалению вопроса: сейчас удаление возможно только после ручного удаления всех комментариев.
9. Определить максимальные длины текстовых полей и правила очистки/экранирования пользовательского HTML.
10. Добавить аудит действий модератора: кто, когда и почему опубликовал, отклонил или снял вопрос.

## 11. Критерии приемки текущей функциональности

1. Пользователь с разрешённой ролью может открыть совещание и создать вопрос с обязательными полями.
2. Вопрос сохраняется как черновик или отправляется на модерацию в зависимости от выбранного действия.
3. Автор может редактировать допустимые статусы и менять адресатов.
4. Модератор может опубликовать вопрос, указав отделы и направление.
5. Модератор может отклонить вопрос с обязательной причиной.
6. Опубликованный вопрос доступен пользователям с ролью в совещании и поддерживает ответы.
7. Модератор может снять опубликованный вопрос с публикации.
8. При наличии комментариев удаление вопроса блокируется.
9. Пользователь без роли не получает вопросы в списке совещания.
10. Недоступные действия возвращают HTTP 403, отсутствующие вопросы и совещания — HTTP 404.
